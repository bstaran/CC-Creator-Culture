# AI 개발 하네스 사용 방법

Claude Code에 작업을 위임하는 절차를 상황별로 정리했습니다. 하네스 설계 배경과 전체 구조는 [README.md](README.md)를 먼저 확인합니다.

## 사전 준비

| 준비 사항 | 이유 |
|---|---|
| 레포 루트에서 Claude Code 실행 | `CLAUDE.md`를 읽어 빌드 명령, 계층 규칙, 금지 사항을 파악한 상태로 시작합니다 |
| JDK 21(`java`가 PATH에 없으면 `JAVA_HOME` 지정) | 빌드, 테스트, 작업 종료 시 컴파일 검증에 사용합니다 |
| `python3` | 안전장치(hook)와 보조 스크립트가 Python으로 작성되어 있습니다 |
| Docker | 서비스 통합 테스트(Testcontainers)와 로컬 전체 스택 실행에 필요합니다. 없으면 통합 테스트를 건너뜁니다 |
| (선택) Antigravity CLI `agy` 설치 및 로그인 | Gemini 문서 교정과 코드 2차 리뷰에 사용합니다. 없으면 해당 단계를 건너뛰며 PR 본문에 그 사실이 남습니다 |

## 역할 분담

| 개발자 | AI |
|---|---|
| 작업 시작 지시 | 작업 분류, 기준 테스트 작성, 구현, 검증, 리뷰, PR 작성 |
| 기능 스펙 승인(`spec: approved` 라벨) | 스펙 초안 작성 |
| PR 리뷰와 머지 | 리뷰 지적 반영(최대 2회) |
| Terraform plan, apply, 배포(CI) | 인프라 변경 초안, 로컬 검증, 예상 plan 요약 |
| 주간 리포트에서 등록할 후보 선택 | 후보 진단, 선택된 후보만 이슈 등록 |

## 작업 요청

### 로컬 환경

모든 작업은 `/triage`로 시작합니다. AI가 작업 유형, 완료 기준, 위험 요소를 정리해 보여 주면 다음 중 하나를 선택합니다.

```text
/triage 주문 취소 시 쿠폰이 복구되지 않는다
/triage #123
```

- **이슈로 등록**: 기록을 남기거나 나중에 처리할 때 선택합니다.
- **지금 진행**: 바로 처리할 때 선택합니다. 이슈가 이미 있으면 아래 작업 유형별 명령으로 이어 갑니다.
- **보류**: 분류 결과만 남기고 종료합니다.

| 작업 종류 | 명령 | 수동 확인 사항 |
|---|---|---|
| 버그 수정 | `/bugfix #번호` | PR 리뷰, 머지 |
| 리팩토링 | `/refactor-task #번호` | PR 리뷰, 머지 |
| 기능 개발 | `/spec <요청>` → 승인 → `/feature #번호` | 스펙 이슈에 `spec: approved` 라벨 부착, PR 리뷰, 머지 |
| 인프라/배포 | `/infra-change #번호` | CI에서 plan 실행 후 결과를 넘겨 대조 요청, apply와 배포 |
| 성능 | `/perf-check #번호` | 측정 계획 승인, 결과 판단 |
| 조사/문서 | `/triage`에서 "지금 진행" | 답변과 코드 근거 확인 |

선택을 확정하기 전까지 AI는 이슈, 브랜치, 라벨을 임의로 만들지 않습니다. 작업 명령을 실행하는 것 자체가 시작 승인입니다.

### GitHub(`@claude`)

다른 팀원에게 넘기거나 로컬 세션 없이 맡길 때 사용합니다. "🤖 AI 작업 요청" 양식으로 이슈를 만든 뒤 댓글을 남깁니다.

1. `@claude`: 분류 결과와 다음 단계만 댓글로 남깁니다. 이 단계에서는 코드를 바꾸지 않습니다.
2. `@claude 진행해`: 작업 유형 라벨을 붙이고, 로컬 명령과 같은 파이프라인으로 처리해 PR을 엽니다. 기능 개발은 스펙 초안까지만 작성합니다.
3. 열린 PR에 `@claude <요청>`: 요청 사항을 수정하고 검증 결과를 댓글로 남깁니다.

팀 멤버가 작성한 이슈와 PR에서만 동작합니다. CI 환경에는 Gemini 도구가 없어 문서 교정과 Gemini 리뷰는 건너뛰며, 현재 CI 토큰 복구 후 사용할 수 있습니다.

## AI PR 리뷰

- **먼저 볼 곳**: PR 본문의 "테스트 결과"(실행한 명령과 테스트 수)와 "참고사항"(리팩토링이면 동작 보존 근거, 반영하지 않은 리뷰 권고와 이유)을 우선 확인합니다.
- **자세한 경과**: `docs/ai-system/tasks/<이슈번호>.md`에 완료 기준, 진행 로그, 리뷰 결과가 남아 있습니다.
- **수정 요청**: PR에 직접 리뷰 코멘트로 남깁니다. 리뷰에서 요청한 수정 빈도가 주간 지표(무수정 승인율)로 집계됩니다.
- **이종 모델 교차 의견**: `/gemini-review #번호`를 실행하면 Gemini가 리뷰한 결과에서 오탐을 걸러 PR 코멘트로 올립니다. 개발자가 직접 작성한 PR에도 사용할 수 있습니다.

## 문서 작성과 교정

PR 본문, 이슈 본문, `docs/` 문서는 `CLAUDE.md`의 "문서 작성" 규칙을 따르며, PR을 만들기 직전에 `/doc-review`로 문장을 다듬습니다. AI가 PR을 생성할 때는 이 단계를 자동으로 거치고, 교정 기록이 없는 문서가 있으면 hook이 PR 생성을 막습니다.

```text
/doc-review                      # 브랜치에서 바뀐 문서
/doc-review docs/ai-system/x.md  # 바뀐 문서 + 지정한 파일
```

## 주간 리포트

매주 월요일 09:00에 `report: weekly` 이슈가 자동으로 생성됩니다. 지난주 머지된 PR, 이슈 현황, 동결된 계층 위반 수와 함께 지난주 변경된 코드에서 찾은 개선 후보가 체크 목록으로 올라옵니다.

1. 등록할 후보를 체크박스로 선택합니다(체크가 등록 승인입니다).
2. 리포트 이슈에 `@claude 체크한 항목을 이슈로 등록해`라고 댓글을 남깁니다. 로컬에서는 `/refactor-audit`에 "주간 리포트 #번호에서 체크한 항목 등록"이라고 요청합니다.
3. 체크된 항목만 `type: ...`, `source: scan` 라벨을 붙여 이슈로 등록하고, 리포트에 `S1 → #N` 형태로 댓글을 남깁니다.
4. 확인이 끝난 리포트 이슈는 닫습니다.

## 차단되는 작업

아래 작업은 hook과 CI 설정이 실행 직전에 차단합니다. 차단되면 AI는 우회하지 않고 사유를 보고합니다.

- PR 머지와 승인, 스펙 승인(`spec: approved`) 라벨 부착
- `dev`, `main`에 직접 push, 강제 push, 원격 브랜치 삭제, `origin` 외 저장소로 push
- `.env`, Terraform 변수와 상태 파일 같은 시크릿 파일 읽기
- `terraform plan/apply/destroy`, 배포 워크플로우 실행, 클라우드 리소스 변경, 컨테이너 이미지 push
- 기존 DB 마이그레이션 수정, 테스트 건너뛰기(`-x test`)

## 작업 중 참고 사항

- **차단 메시지 확인**: AI가 하면 안 되는 위험한 명령이나 금지 작업을 hook이 막은 결과입니다. 규칙을 우회하지 말고 사유를 확인한 뒤, 꼭 필요한 예외라면 `.claude/hooks/`를 수정하는 PR을 엽니다.
- **종료 전 컴파일 대기**: 커밋하지 않은 Java 변경 사항이 있으면 세션 종료 직전에 컴파일과 포맷 검사가 자동으로 실행됩니다(같은 내용에 대해서는 다시 실행하지 않습니다).
- **세션 복구**: 상태 파일(`docs/ai-system/tasks/<이슈번호>.md`)이 남아 있으면 같은 명령(`/bugfix #번호` 등)을 다시 실행해 중단된 단계부터 이어 갑니다.
- **머지 기준**: AI가 만든 PR도 팀원이 작성한 PR과 같은 기준으로 리뷰한 뒤 직접 머지합니다.

## 명령어 요약

| 명령 | 언제 | 하는 일 |
|---|---|---|
| `/triage <요청 또는 #번호>` | 모든 작업의 시작 | 작업 분류, 완료 기준과 위험 요소 정리 |
| `/bugfix #번호` | 버그 이슈 | 재현 테스트 → 수정 → 검증 → 리뷰 → PR |
| `/refactor-task #번호` | 리팩토링 이슈 | 특성 테스트 → 정리 → 검증 → 리뷰 → PR |
| `/characterize <대상>` | 수정 전 동작 고정이 필요할 때 | 현재 동작을 테스트로 고정 |
| `/spec <요청>` | 기능 개발 시작 | 스펙 초안을 이슈로 작성하고 승인 요청 |
| `/feature #번호` | 스펙 승인 후 | 요구사항 테스트 → 구현 → 검증 → 리뷰 → PR |
| `/infra-change #번호` | 인프라/배포 변경 | 변경 초안, 로컬 검증, 예상 plan 요약 → PR |
| `/perf-check #번호` | 성능 확인, 개선 | 측정 계획 → 로컬 환경 기준선 비교 |
| `/refactor-audit [서비스]` | 정기 점검 | 개선 후보 진단, 선택된 후보만 이슈 등록 |
| `/doc-review [파일]` | 문서, PR 본문 작성 후 | Gemini 기반 문장 교정 |
| `/gemini-review [#번호]` | PR 직전, 열린 PR 리뷰 | Gemini 기반 코드 2차 리뷰 |
