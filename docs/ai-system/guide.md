# AI 작업 사용 방법

AI(Claude Code)에게 일을 맡기는 방법을 상황별로 정리했다. 하네스가 무엇이고 왜 이렇게 동작하는지는 [README.md](README.md)를 먼저 읽는다.

## 처음 한 번 준비

| 준비 | 이유 |
|---|---|
| 레포 루트에서 Claude Code 실행 | AI가 `CLAUDE.md`를 읽어 빌드 명령, 규칙, 금지 사항을 알고 시작한다 |
| JDK 21(`java`가 PATH에 없으면 `JAVA_HOME` 지정) | 빌드, 테스트, 작업 종료 시 컴파일 확인에 쓴다 |
| `python3` | 안전장치(hook)와 보조 스크립트가 Python으로 작성되어 있다 |
| Docker | 서비스 통합 테스트(Testcontainers)와 로컬 전체 스택에 필요하다. 없으면 통합 테스트를 건너뛴다 |
| (선택) Antigravity CLI `agy` 설치 후 대화형으로 한 번 로그인 | Gemini 문서 교정과 코드 2차 리뷰에 쓴다. 없으면 그 단계는 건너뛰고 PR에 그 사실이 적힌다 |

## 사람과 AI의 역할

| 사람이 한다 | AI가 한다 |
|---|---|
| 작업 시작 지시 | 분류, 기준 테스트, 구현, 검증, 리뷰, PR 작성 |
| 기능 스펙 승인(`spec: approved` 라벨) | 스펙 초안 작성 |
| PR 리뷰와 머지 | 리뷰 지적 반영(최대 2회) |
| Terraform plan, apply, 배포(CI) | 인프라 변경 초안과 로컬 검증, 예상 plan 요약 |
| 주간 리포트에서 등록할 후보 고르기 | 후보 진단, 고른 후보만 이슈 등록 |

## 일을 맡길 때

### 로컬에서

무엇을 하든 `/triage`로 시작한다. AI가 작업 종류, 완료 기준, 위험 요소를 정리해 보여 주고, 사람이 다음 중 하나를 고른다.

```text
/triage 주문 취소 시 쿠폰이 복구되지 않는다
/triage #123
```

- **이슈로 등록**: 기록을 남기거나 나중에 처리할 때
- **지금 진행**: 바로 처리할 때. 이슈가 있으면 아래 작업 종류별 명령으로 이어 간다
- **보류**: 분류 결과만 남긴다

| 작업 종류 | 명령 | 사람이 할 일 |
|---|---|---|
| 버그 수정 | `/bugfix #번호` | PR 리뷰, 머지 |
| 리팩토링 | `/refactor-task #번호` | PR 리뷰, 머지 |
| 기능 개발 | `/spec <요청>` → 승인 → `/feature #번호` | 스펙 이슈에 `spec: approved` 라벨 부착, PR 리뷰, 머지 |
| 인프라/배포 | `/infra-change #번호` | CI에서 plan 실행, 결과를 AI에게 넘겨 대조, apply와 배포 |
| 성능 | `/perf-check #번호` | 측정 계획 승인, 결과 판단 |
| 조사/문서 | `/triage`에서 "지금 진행" | 답변과 근거 확인 |

AI는 사람이 고르기 전에는 이슈, 브랜치, 라벨을 만들지 않는다. 작업 명령을 실행하는 것이 시작 승인이다.

### GitHub에서(`@claude`)

다른 사람에게 넘기거나 로컬 세션 없이 맡길 때 쓴다. "🤖 AI 작업 요청" 양식으로 이슈를 만든 뒤 댓글을 단다.

1. `@claude`: AI가 분류 결과와 다음 단계를 댓글로 남긴다. 이 단계에서는 아무것도 바꾸지 않는다.
2. `@claude 진행해`: AI가 작업 종류 라벨을 붙이고, 위 명령과 같은 절차로 처리해 PR을 연다. 기능 개발은 스펙 초안까지만 작성한다.
3. 열린 PR에 `@claude <요청>`: AI가 수정하고 검증 결과를 댓글로 남긴다.

팀 멤버가 쓴 이슈와 PR에서만 동작한다. CI에는 Gemini 도구가 없어서 문서 교정과 Gemini 리뷰는 건너뛴다. 현재 CI 토큰에 문제가 있어 복구한 뒤부터 쓸 수 있다.

## AI가 만든 PR을 리뷰할 때

- **먼저 볼 곳**: PR 본문의 "테스트 결과"(실행한 명령과 테스트 수)와 "참고사항"(리팩토링이면 동작이 그대로인 근거, 반영하지 않은 리뷰 지적과 이유)
- **자세한 경과**: `docs/ai-system/tasks/<이슈번호>.md`에 기준, 진행 로그, 리뷰 결과가 있다
- **고칠 점**: PR에 직접 리뷰 코멘트로 남긴다. 사람이 고친 정도가 주간 지표(무수정 승인율)로 잡힌다
- **다른 모델 의견이 더 필요할 때**: `/gemini-review #번호`를 실행하면 Gemini가 리뷰하고, AI가 오탐을 걸러 PR에 코멘트로 올린다. 사람이 만든 PR에도 쓸 수 있다

## 문서를 쓸 때

PR 본문, 이슈 본문, `docs/` 문서는 `CLAUDE.md`의 "문서 작성" 규칙을 따르고, PR을 만들기 직전에 `/doc-review`로 문장을 교정한다. AI가 PR을 만들 때는 이 단계를 자동으로 거치며, 교정하지 않은 문서가 있으면 PR 생성이 막힌다.

```text
/doc-review                      # 브랜치에서 바뀐 문서
/doc-review docs/ai-system/x.md  # 바뀐 문서 + 지정한 파일
```

## 주간 리포트

매주 월요일 09:00에 `report: weekly` 이슈가 자동으로 생긴다. 지난주에 머지된 PR, 이슈 현황, 계층 위반 수와 함께, 지난주에 바뀐 코드에서 찾은 개선 후보가 체크 목록으로 들어 있다.

1. 등록할 후보를 체크한다(체크가 승인이다).
2. 리포트에 `@claude 체크한 항목을 이슈로 등록해`라고 댓글을 단다. 로컬에서는 `/refactor-audit`에 "주간 리포트 #번호에서 체크한 항목 등록"이라고 요청한다.
3. 확인이 끝난 리포트 이슈는 닫는다.

## AI가 할 수 없는 일

아래 일은 hook과 CI 설정이 실행 직전에 막는다. 막히면 AI는 우회하지 않고 사유를 보고한다.

- PR 머지와 승인, 스펙 승인 라벨 부착
- `dev`, `main`에 직접 push, 강제 push, 원격 브랜치 삭제, `origin` 외 저장소로 push
- `.env`, Terraform 변수와 상태 파일 같은 비밀 값 읽기
- `terraform plan/apply/destroy`, 배포 워크플로우 실행, 클라우드 자원 변경, 이미지 push
- 기존 DB 마이그레이션 수정, 테스트 건너뛰기(`-x test`)

## 작업 중 알아 둘 것

- **차단 메시지가 나오면**: AI가 하면 안 되는 일(머지, `dev`/`main` push, 비밀 값 접근, `terraform apply` 등)을 hook이 막은 것이다. 규칙을 우회하지 말고 사유를 확인한다. 꼭 필요한 작업이 막힌다면 `.claude/hooks/`를 고치는 PR을 올린다.
- **작업을 끝낼 때 기다리는 시간**: 커밋하지 않은 Java 변경사항이 있으면 끝내기 전에 컴파일과 포맷 검사가 자동으로 실행된다(같은 내용은 다시 실행하지 않는다).
- **세션이 끊겼을 때**: 상태 파일(`docs/ai-system/tasks/<이슈번호>.md`)이 있으면 같은 명령(`/bugfix #번호` 등)을 다시 실행해 이어 간다.
- **머지**: 항상 사람이 한다. AI가 만든 PR도 사람이 만든 PR과 같은 기준으로 리뷰한다.

## 명령 한눈에 보기

| 명령 | 언제 | 하는 일 |
|---|---|---|
| `/triage <요청 또는 #번호>` | 모든 작업의 시작 | 작업 분류, 완료 기준과 위험 요소 정리 |
| `/bugfix #번호` | 버그 이슈 | 재현 테스트 → 수정 → 검증 → 리뷰 → PR |
| `/refactor-task #번호` | 리팩토링 이슈 | 특성 테스트 → 정리 → 검증 → 리뷰 → PR |
| `/characterize <대상>` | 고치기 전 현재 동작을 고정하고 싶을 때 | 현재 동작을 테스트로 고정 |
| `/spec <요청>` | 기능 개발 시작 | 스펙 초안을 이슈로 작성하고 승인 요청 |
| `/feature #번호` | 스펙 승인 뒤 | 요구사항 테스트 → 구현 → 검증 → 리뷰 → PR |
| `/infra-change #번호` | 인프라/배포 변경 | 변경 초안, 로컬 검증, 예상 plan 요약 → PR |
| `/perf-check #번호` | 성능 확인, 개선 | 측정 계획 → 로컬에서 기준선과 비교 |
| `/refactor-audit [서비스]` | 정기 점검 | 개선 후보 진단, 고른 후보만 이슈 등록 |
| `/doc-review [파일]` | 문서, PR 본문 작성 뒤 | Gemini로 문장 교정 |
| `/gemini-review [#번호]` | PR 직전, 열린 PR 리뷰 | Gemini로 코드 2차 리뷰 |
