## 기준

- **바꾸는 것**: 세 서비스(`OrderCancellationTransactionService`, `OrderPaymentResultService`, `OrderExpirationTransactionService`)에 복사된 세 가지 변환 로직을 한 곳으로 모은다.
  - 주문 항목을 재고 복구 항목(`StockItem`)으로 바꾸는 로직(세 서비스)
  - 쿠폰 복구 대상 ID를 모아 복구를 호출하는 로직(결제 실패, 만료)
  - 상품별 수량을 합산하는 로직(취소, 결제 성공)
- **바뀌면 안 되는 것**: 재고 복구 요청의 항목과 순서, 쿠폰 복구 호출 여부와 인자(중복 제거, null 제외, 처음 나온 순서), outbox에 쓰는 이벤트 페이로드(`OrderPaidEvent`, `OrderCanceledEvent`의 상품별 수량)
- **기존 테스트 확인 결과**:
  - 결제 결과(`OrderPaymentResultServiceTest`): 재고 항목 순서, 쿠폰 중복 제거, 쿠폰 없는 주문, 결제 이벤트 수량 합산을 모두 단언해 기존 테스트만으로 충분하다.
  - 취소: 재고 항목은 통합 테스트가 순서와 무관하게 단언하지만, `OrderCanceledEvent`의 상품별 수량은 어느 테스트도 단언하지 않는다(Kafka 테스트는 주문 ID만 확인).
  - 만료(`OrderExpirationTransactionServiceTest`): 재고 항목은 개수만 확인하고, 쿠폰 중복 제거와 null 제외는 단언하지 않는다.
- **완료 기준**: 아래 특성 테스트와 기존 테스트가 리팩토링 전후 모두 통과하고, 테스트 수가 줄지 않는다.
- **고정 파일**:
  - `OrderCancellationTransactionServiceTest`(신규 2개): 취소 이벤트의 상품별 수량 합산, 재고 항목 순서
  - `OrderExpirationTransactionServiceTest`(신규 3개): 쿠폰 중복 제거와 처음 나온 순서, 재고 항목 순서, 쿠폰 없는 주문
  - 기존 기준: `OrderPaymentResultServiceTest`, `OrderCancellationIntegrationTest`, `OrderPaymentResultServiceIntegrationTest`, `OrderExpirationServiceIntegrationTest`
- **리팩토링 전 기준 수치**: `./gradlew :apps:order-service:test` 786개, 실패 0, 건너뜀 1(기존 비활성 `CartConcurrencyTest`). Docker 통합 테스트 실행됨

## 결정 사항

- 결제 결과 쪽은 기존 테스트로 충분하다고 판단해 특성 테스트를 추가하지 않는다.
- 쿠폰 ID 목록과 상품별 수량은 순수 데이터 계산이라 도메인 `Order`에 두고, 재고 복구 항목(`StockPort.StockItem`)은 application 타입이라 `StockRestoreCommand.of()`에 둔다. 도메인이 application을 import하지 않아 새 계층 위반이 없다.
- 쿠폰 복구 호출(목록이 비면 호출하지 않음)은 두 서비스에 세 줄씩 남긴다. 포트에 기본 메서드를 두는 방법도 있지만 범위 밖이라 후속 제안으로 둔다.

## 시스템 검증에서 발견한 점

- implementer가 빌드 종료 코드를 확인하지 못하고 테스트 결과 XML만으로 보고해, 오케스트레이터가 빌드를 직접 실행해 확인했다. 지침에 "종료 코드를 함께 보고한다"는 항목을 넣을지 검토한다.
- 리뷰어(arch, event)는 Read, Grep, Glob만 있어 `git diff`를 실행할 수 없다. 절차(`group-a.md` 6단계)에는 diff 전체를 넘기라고 되어 있는데 오케스트레이터가 diff 명령만 넘겼고, 리뷰어들은 대신 원본 체크아웃의 파일과 비교해 확인했다. 절차 문구를 "diff 출력 내용을 프롬프트에 붙인다"로 분명히 한다.
- 특성 테스트 작성, 구현, 리뷰 3종이 모두 수정 요청 없이 한 번에 통과했다(수정 요청 회차 0).
