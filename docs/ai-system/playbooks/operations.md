# 운영 절차(5단계)

AI 작업 체계를 계속 돌리기 위한 큰 루프다(plan.md 9장). 주간 루프에서는 자동으로 리포트를 만들고, 사람은 후보를 고른다. 월간 루프에서는 지표를 보고 자동화 범위와 모델 배치를 다시 정한다.

## 주간: 자동 리포트

`.github/workflows/ai-weekly.yml`이 매주 월요일 09:00(KST)에 실행되어 지난주 월요일부터 일요일까지(UTC)를 집계하고 **주간 리포트 이슈**(`report: weekly` 라벨) 하나를 만든다.

| 단계 | 하는 일 | 사용하는 것 |
|---|---|---|
| 지표 | 어제까지 7일 동안 머지된 PR(트랙별 수, AI 무수정 승인, 변경 줄 수, 리드타임, 유입 경로), 새 이슈와 열린 이슈, 동결된 계층 위반 수를 모은다 | `scripts/ai/weekly-metrics.py`(Claude 사용 안 함) |
| 정기 스캔 | 같은 기간에 바뀐 소스 파일만 진단해 이슈 후보를 체크 목록으로 만든다. 바뀐 파일이 없으면 건너뛴다 | `/refactor-audit --weekly`(Claude, `CLAUDE_CODE_OAUTH_TOKEN`) |
| 리포트 | 지표와 스캔 결과를 이슈 하나로 남긴다. 스캔이 실패해도 지표만으로 만든다 | `gh issue create` |

사람이 할 일:
1. 리포트에서 등록할 후보를 체크한다(체크가 승인이다).
2. 리포트 이슈에 `@claude 체크한 항목을 이슈로 등록해`라고 댓글을 남긴다. 로컬에서는 `/refactor-audit`에 "주간 리포트 #<번호>에서 체크한 항목 등록"이라고 요청한다.
3. AI는 체크된 항목만 `type: ...`, `source: scan` 라벨로 등록하고, 리포트에 "S1 → #N" 댓글을 남긴다.
4. 리포트 이슈는 확인이 끝나면 닫는다. 다음 스캔에서는 지난 리포트와 겹치는 후보를 제외한다.

수동 실행: Actions 탭에서 "AI Weekly Report"를 직접 실행한다(기간 일수, 스캔 여부 선택). AI는 워크플로우를 실행하지 않는다(hook 차단).

### 지표 정의

| 지표 | 계산 |
|---|---|
| AI PR | `ai: generated` 라벨이 붙은 PR. AI가 PR을 만들 때 붙인다 |
| AI 무수정 승인 | PR을 연 뒤 추가 커밋이나 변경 요청 리뷰 없이 머지된 AI PR 수 / AI PR 수. 커밋 시각으로 판단하므로 PR을 연 뒤 rebase하면 수정으로 센다 |
| 리드타임 | PR 생성부터 머지까지. 기능 개발의 스펙 승인부터 머지까지는 월간 리뷰에서 직접 계산한다 |
| 유입 경로 | PR이 닫는 이슈(`Closes #N`)의 `source:` 라벨. 연결된 이슈가 없으면 "이슈 없음" |
| 동결된 계층 위반 | `archunit_store`의 위반 클래스 수(내부 클래스 포함)와 의존 수. 줄어들면 개선된 것이다 |

로컬에서 같은 지표를 볼 때:

```bash
python3 scripts/ai/weekly-metrics.py                                   # 어제까지 7일(양 끝 포함)
python3 scripts/ai/weekly-metrics.py --since 2026-11-01 --until 2026-11-30 --coverage
```

## 월간: 지표 리뷰

매월 첫 주에 지난달 주간 리포트를 모아 한 번 리뷰하고, 결과를 `metrics.md`의 "월간 리뷰"에 추가한다.

1. **지표 모으기**: `weekly-metrics.py --since <지난달 1일> --until <지난달 말일>`로 한 달치를 다시 계산한다.
2. **커버리지**: 로컬에서 `./gradlew test --continue`를 실행한 뒤 `--coverage`로 커버리지 표를 붙인다(주간 실행에서는 테스트를 돌리지 않는다).
3. **판단**: 아래 항목을 보고 결정한 것만 기록한다.

| 확인 | 판단 |
|---|---|
| 트랙별 AI 무수정 승인율 | 자동화 확대 기준(plan.md 14장)을 채운 트랙이 있는지 확인한다 |
| PR 변경 줄 수 중앙값 | 커지고 있으면 이슈를 더 잘게 나누도록 `/refactor-audit` 크기 기준을 조정한다 |
| 리뷰 회차, 사람 수정 내용(파이프라인 검증 기록) | 2회 이상 반복된 지적은 `CLAUDE.md`, 에이전트 지침, hooks에 반영한다 |
| 정기 스캔 후보 중 등록 비율 | 등록되지 않는 유형이 반복되면 점검표에서 빼거나 기준을 바꾼다 |
| 동결된 계층 위반 수 | 줄어드는 속도를 확인하고, 늘었다면 원인을 파악한다(CI가 막아야 정상) |
| 사용량 | 구독 사용량 화면에서 확인한다. 예산을 넘으면 모델 배치나 CI 자동 실행 범위를 줄인다 |

4. **기록**: `metrics.md`의 "월간 리뷰"에 지표 요약 표와 결정 사항을 남긴다. 규칙을 바꾸기로 했으면 해당 문서를 고치는 PR을 따로 연다.

## CI 토큰 복구 후 첫 확인

`CLAUDE_CODE_OAUTH_TOKEN`을 복구하면 아래 항목을 한 번씩 확인한다. 결과는 `metrics.md` 파이프라인 검증 기록에 남긴다.

| 대상 | 확인 방법 | 볼 것 |
|---|---|---|
| `ai-weekly.yml` | Actions 탭에서 직접 실행(스캔 켬, 끔 한 번씩) | scan job 로그의 허용 도구 목록에 `./gradlew`, `terraform`, `gh pr`가 없는지, `.ai-cache/weekly/scan.md`가 만들어지는지, 리포트 본문에 토큰처럼 보이는 문자열이 없는지 |
| `claude.yml` 분류 | 테스트 이슈에 `@claude` | `/triage` 결과 댓글만 남기고 코드, 브랜치, 라벨을 바꾸지 않는지 |
| `claude.yml` 진행 | 같은 이슈에 `@claude 진행해` | 트랙 라벨, 브랜치, PR이 만들어지는지, AI가 만든 PR에서 모듈 CI가 실행되는지(워크플로우 토큰으로 만든 PR은 다른 워크플로우를 실행하지 않는다) |
| `claude.yml` 주간 리포트 | 리포트 이슈에서 후보를 체크하고 `@claude 체크한 항목을 이슈로 등록해` | 체크한 후보만 `source: scan` 이슈로 등록되고 리포트에 "S1 → #N" 댓글이 남는지 |
| hook | 위 실행 로그 | `guard_bash.py`가 CI에서도 동작하는지(머지, 승인, `spec: approved` 차단) |
