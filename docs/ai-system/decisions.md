# 하네스 설계 결정

AI 개발 하네스를 만들면서 내린 주요 결정과 그 이유를 기록한다. 결정마다 상황, 결정, 이유, 결과 순서로 쓴다. 전체 소개는 [README.md](README.md), 초기 설계안 전문은 [plan.md](plan.md)에 있다.

## 1. 완료 기준의 위치에 따른 작업 분류(2026-11-18)

- **상황**: 리팩토링, 버그 수정, 기능 개발, 인프라 변경을 같은 방식으로 AI에게 맡기면, 결과가 맞는지 판정하는 방법이 작업마다 달라 자동화 범위를 정할 수 없다.
- **결정**: 완료 기준이 레포 안에 있는 작업(A: 리팩토링, 버그 수정), 사람이 새로 정해야 하는 작업(B: 기능 개발, 조사), 실행 환경에서만 확인되는 작업(C: 인프라, 성능)으로 나눈다.
- **이유**: 기준이 이미 있는 A는 AI가 PR까지 맡을 수 있지만, B는 사람이 스펙을 승인해야 기준이 생기고, C는 적용 자체가 외부에 영향을 준다. 그룹을 나누면 그룹마다 "AI가 어디까지 하는가"를 한 번에 정할 수 있다.
- **결과**: 그룹마다 절차(스킬)와 리뷰어를 따로 두었다. 상세 기준은 [plan.md](plan.md) 3장에 있다.

## 2. 기준 테스트 선행 커밋(2026-11-18)

- **상황**: AI가 구현과 테스트를 함께 고치면, 테스트가 구현에 맞춰 바뀌어 검증이 무의미해질 수 있다.
- **결정**: 구현 전에 기준 테스트를 먼저 커밋한다. 리팩토링은 현재 동작을 고정하는 특성 테스트, 버그 수정은 버그 때문에 실패하는 재현 테스트, 기능 개발은 승인된 스펙의 요구사항 테스트를 쓴다. 기준을 커밋한 뒤에는 테스트 파일을 바꾸지 않는다.
- **이유**: 기준 커밋과 구현 커밋을 나누면 리뷰하는 사람이 "테스트가 바뀌지 않았고 통과한다"만 확인해도 동작 보존이나 버그 수정을 판단할 수 있다.
- **결과**: #5에서는 재현 테스트 4개가 실패하는 상태를 먼저 커밋했고, #7에서는 특성 테스트 5개를 먼저 커밋한 뒤 테스트 파일을 바꾸지 않았다.

## 3. 구축 후 일괄 검증(2026-11-20)

- **상황**: 원래 계획은 그룹 A를 도입하고 검증한 뒤 B, C로 넘어가는 순서였다.
- **결정**: 모든 그룹의 도구를 먼저 만든 뒤 그룹별로 실제 작업을 한꺼번에 검증한다. 그룹 A만 공통 뼈대를 확인하려고 1건(#5)을 먼저 검증했다.
- **이유**: 공통 절차(상태 파일, 리뷰 흐름, 문서 교정)가 B, C를 만들면서 계속 바뀌었다. 단계마다 검증하면 공통 절차가 바뀔 때마다 앞선 검증을 다시 해야 한다.
- **결과**: 일괄 검증에서 나온 결함은 모아서 한 번에 고친다.

## 4. 사람이 맡는 결정(2026-11-18)

- **상황**: 작업 루프 전체를 자동화할 수도 있지만, 결과가 의도대로인지 판단하는 일은 아직 사람이 해야 한다.
- **결정**: 처음에는 정기 스캔과 리뷰만 자동으로 돌리고, 작업 시작, 스펙 승인, 머지, Terraform plan과 apply, 배포는 사람이 한다.
- **이유**: 되돌리기 어려운 결정을 사람에게 남겨 두면 AI가 잘못 판단해도 영향이 PR 안에 머문다.
- **결과**: 작업 종류별로 AI PR의 무수정 승인율을 측정한다. 확대 기준(최근 10건 무수정 승인, 회귀 0건)은 아래 "남은 결정"에 있다.

## 5. 역할별 모델 배치(2026-11-18)

- **상황**: 모든 일을 가장 강한 모델 하나로 처리하면 사용 한도가 빠르게 줄고, 긴 세션에서는 읽은 파일이 쌓여 품질이 떨어진다.
- **결정**: 코드 탐색은 Haiku, 기준이 고정된 뒤의 구현과 테스트 작성은 Sonnet, 작업 지휘와 리뷰는 Opus가 맡는다. 서브에이전트는 읽은 내용을 그대로 옮기지 않고 근거(파일과 줄)가 붙은 요약만 돌려준다.
- **이유**: 탐색은 많이 읽고 짧게 보고하는 일이라 가벼운 모델로 충분하다. 리뷰어는 작성자보다 약하면 안 되므로 Opus를 쓴다.
- **결과**: 에이전트 정의 파일(`.claude/agents/`)에 모델과 effort를 고정했다. 리뷰어는 읽기 도구만 쓸 수 있다.

## 6. 지휘 AI의 직접 검증(2026-11-19)

- **상황**: 첫 검증 작업(#5)에서 테스트 작성 에이전트가 실행 결과 없이 끝났고, 구현 에이전트는 통과한 테스트 수 없이 "BUILD SUCCESSFUL"만 보고했다.
- **결정**: 서브에이전트의 보고는 참고 자료로만 쓴다. 통과 여부와 테스트 수는 작업을 지휘하는 AI가 빌드와 테스트를 직접 실행한 결과로 판단한다.
- **이유**: 보고만 믿으면 실제로 실행하지 않은 검증이 PR 본문에 "통과"로 남을 수 있다.
- **결과**: 절차(`playbooks/group-a.md`)와 에이전트 지침에 반영했다. #7에서는 구현 에이전트가 종료 코드를 확인하지 못했지만, 지휘 AI가 직접 실행해 확인했다.

## 7. 기존 계층 위반 동결(2026-11-18)

- **상황**: 계층 규칙 테스트(ArchUnit)를 처음 넣었을 때, `application`이 `presentation`이나 `infrastructure`에 의존하는 기존 위반이 34개 클래스, 176건 있었다.
- **결정**: 기존 위반은 현재 상태로 동결하고, 새 위반만 테스트 실패로 처리한다. 동결 목록에 위반을 직접 추가하는 것은 금지한다.
- **이유**: 한 번에 고치면 PR이 커지고 동작 변경 위험이 크다. 동결하면 더 나빠지지 않게 막으면서, 하네스를 검증한 뒤 리팩토링 작업으로 하나씩 줄일 수 있다.
- **결과**: 위반 수를 주간 지표로 추적한다. 기존 위반을 고치면 동결 목록에서 자동으로 빠진다.

## 8. 이벤트 스키마 스냅샷 테스트(2026-11-19)

- **상황**: Kafka 이벤트 클래스는 여러 서비스가 함께 쓰므로, 필드 하나를 바꿔도 다른 서비스의 소비자가 깨질 수 있다.
- **결정**: 이벤트의 직렬화 구조를 스냅샷 파일로 고정하고, 구조가 바뀌면 테스트가 실패하게 한다. API 스키마는 컨트롤러 테스트로 고정한다.
- **이유**: 별도 스키마 레지스트리를 도입하지 않고도, 기능 개발에서 이벤트 구조가 의도치 않게 바뀌는 것을 기계적으로 잡을 수 있다.
- **결과**: `EventSchemaSnapshotTest`가 이벤트 구조를 검사한다. 의도한 변경일 때만 스냅샷을 갱신해 함께 커밋한다.

## 9. 인프라 작업의 클라우드 자격 증명 미부여(2026-11-19)

- **상황**: 인프라 변경을 검증하려면 Terraform plan이 필요하지만, plan을 실행하려면 클라우드 자격 증명이 필요하다.
- **결정**: AI에게는 클라우드 자격 증명을 주지 않는다. AI는 자격 증명 없이 도는 로컬 검증(`terraform fmt`, `validate`, `test`)과 예상 plan 요약까지 하고, plan은 사람이 CI에서 실행한 뒤 그 결과를 AI가 예상과 대조한다. 격리 환경은 로컬 compose만 쓴다.
- **이유**: 자격 증명이 있으면 차단 규칙이 뚫렸을 때 실제 자원이 바뀔 수 있다. 자격 증명 자체를 주지 않는 편이 가장 확실하다.
- **결과**: hook이 `terraform plan/apply/destroy`와 클라우드 CLI 쓰기 명령을 막는다.

## 10. 성능 판정 기준(2026-11-19)

- **상황**: 부하 테스트 결과는 실행할 때마다 흔들려서, 한 번 측정한 값으로 회귀를 판정하면 오판이 생긴다.
- **결정**: 같은 시나리오를 3회 실행해 중앙값을 기준선과 비교하고, p95 응답 시간이 10%를 넘게 늘거나 실패율이 1%p를 넘게 늘면 실패로 판정한다.
- **이유**: 반복 측정과 허용 오차를 정해 두면 AI가 측정 노이즈를 성능 변화로 착각하지 않는다.
- **결과**: 이 기준을 `scripts/ai/perf-compare.py`의 기본값으로 정했다.

## 11. 다른 모델의 문서 교정(2026-11-19, 2026-11-20 갱신)

- **상황**: AI가 쓴 PR 본문과 문서는 서술어가 빠지거나 맥락 없는 짧은 문장이 많았다. 같은 모델에게 교정을 맡기면 자기 문장의 문제를 잘 찾지 못한다.
- **결정**: 사람이 읽는 문서는 PR 직전에 다른 회사 모델(Gemini, Antigravity CLI)로 교정한다. 바뀐 부분만 묶어 한 번에 보내고, 교정 기록이 없으면 PR 생성을 막는다. 기본 모델은 `gemini-4-neon-medium`이다.
- **이유**: 가벼운 Gemini 모델(hydrogen)과 그보다 강한 모델(neon)을 비교했다. 이름 끝의 `medium`, `high`는 생각 수준이다. hydrogen은 명백한 오류만 찾고 서술어 누락, 의미 중복 같은 문제를 놓쳤다. Antigravity CLI는 호출마다 고정 비용(입력 약 1.1만 토큰, 약 10초)이 커서 호출 횟수를 줄이는 쪽으로 설계했다.
- **결과**: 호출 수가 18회에서 3회로 줄었고, 심은 오류 10개는 모두 찾았다. 측정값은 [metrics.md](metrics.md)에 있다.

## 12. 다른 모델의 코드 2차 리뷰(2026-11-20)

- **상황**: Claude 리뷰어끼리는 같은 계열 모델이라 같은 문제를 함께 놓칠 수 있다. CI에서 다른 모델 리뷰를 돌리려면 API 키나 Google Cloud 자격 증명이 필요하고, 개인 구독을 CI에서 쓰는 공식 방법은 없다.
- **결정**: Claude 리뷰어를 통과한 뒤 PR 직전에 로컬에서 Gemini(`gemini-4-neon-high`)로 2차 리뷰를 한 번 한다. 열린 PR에서는 오탐을 거른 결과만 PR 리뷰 코멘트로 올린다. Claude CI 리뷰는 그대로 두고, 어느 쪽을 계속 쓸지는 나중에 정한다.
- **이유**: 공개 저장소에 self-hosted runner를 붙이면 외부 PR이 로컬 환경에서 코드를 실행할 수 있어 쓰지 않았다.
- **결과**: 버그 4개를 심은 브랜치에서 4개를 모두 찾았고, [PR #12](https://github.com/bstaran/CC-Creator-Culture/pull/12)에서는 Claude 리뷰어가 놓친 실제 버그 2건을 찾았다.

## 13. 변경된 파일 중심의 정기 스캔(2026-11-20)

- **상황**: 매주 전체 코드를 진단하면 사용량이 크고, 후보를 바로 이슈로 등록하면 쓸모없는 이슈가 쌓인다.
- **결정**: 매주 지난 7일 동안 바뀐 소스 파일만 진단한다. 후보는 주간 리포트 이슈의 체크 목록에 올리고, 사람이 체크한 항목만 이슈로 등록한다. 지표 수집은 AI 없이 스크립트로 한다.
- **이유**: 바뀐 파일에 새 문제가 생길 가능성이 가장 높다. 체크를 승인으로 쓰면 사람이 고르는 단계를 지키면서도 손이 적게 간다.
- **결과**: `.github/workflows/ai-weekly.yml`에 구현했다. CI 토큰을 복구한 뒤 처음 실행해 확인한다.

## 14. 위험 명령의 이중 차단(2026-11-20)

- **상황**: hook으로 위험 명령을 막아도, 명령 형태를 바꾸면 빠져나갈 수 있다. CI 연동 리뷰([PR #14](https://github.com/bstaran/CC-Creator-Culture/pull/14))에서 push 차단을 우회하는 형태가 지적됐다.
- **결정**: hook에서는 알려진 우회 형태(force push 변형, 원격 브랜치 삭제, git 설정을 이용한 명령 실행 등)를 하나씩 막고, 차단과 허용 사례를 회귀 테스트로 고정한다. 그와 별개로 GitHub의 `dev`, `main` 브랜치 보호를 마지막 경계로 둔다. CI에서는 기본 토큰을 읽기 전용으로 두고, push와 PR 생성은 Claude GitHub App 토큰으로만 한다.
- **이유**: 명령 문자열 검사만으로는 모든 우회를 막을 수 없다. AI 쪽 차단과 저장소 설정을 함께 두어야 한쪽이 뚫려도 피해가 없다.
- **결과**: 차단 규칙 회귀 테스트를 65개에서 100개로 늘렸다.

## 15. 이슈의 `@claude` 호출 시 분류 우선(2026-11-20)

- **상황**: 이슈에서 `@claude`를 부르면 AI가 바로 코드를 고치기 시작할 수 있다.
- **결정**: 첫 호출은 `/triage` 분류 결과만 댓글로 남기고 아무것도 바꾸지 않는다. 사람이 `@claude 진행해`라고 요청해야 작업을 시작한다. 팀 멤버가 쓴 이슈와 댓글에서만 동작한다.
- **이유**: 로컬에서 쓰는 방식(분류 뒤 사람이 고름)과 같게 맞추고, 외부인이 이슈로 AI 작업을 시키는 것을 막는다.
- **결과**: `.github/workflows/claude.yml`에 구현했다. CI 토큰을 복구한 뒤 확인한다.
