# 하네스 설계 결정

AI 개발 하네스를 구축하면서 내린 주요 결정과 배경을 정리했습니다. 전체 개요는 [README.md](README.md), 초기 설계안 원문은 [plan.md](plan.md)에 있습니다.

## 1. 완료 기준의 위치에 따른 작업 분류(2026-11-18)

- **상황**: 리팩토링, 버그 수정, 기능 개발, 인프라 변경을 똑같은 절차로 AI에 맡기면 결과 판정 방식이 작업마다 달라 자동화 경계를 정할 수 없습니다.
- **결정**: 완료 기준이 레포 내부에 있는 작업(A: 리팩토링, 버그 수정), 새로 정의해야 하는 작업(B: 기능 개발, 조사), 실행 환경에서만 검증되는 작업(C: 인프라, 성능)으로 나눴습니다.
- **이유**: 기준이 이미 존재하는 A는 AI가 PR 생성까지 처리할 수 있지만, B는 스펙 승인 전까지 기준이 없고 C는 적용 자체가 외부 환경에 영향을 주기 때문입니다. 그룹별로 AI 위임 범위를 일괄 지정할 수 있게 했습니다.
- **결과**: 트랙별 스킬과 리뷰어를 분리해 배치했습니다. 상세 기준은 [plan.md](plan.md) 3장에 있습니다.

## 2. 기준 테스트 선행 커밋(2026-11-18)

- **상황**: AI가 구현 코드와 테스트 코드를 함께 수정하면, 테스트가 바뀐 구현에 맞춰져 검증 자체가 무의미해질 수 있습니다.
- **결정**: 구현 전에 기준 테스트를 먼저 커밋합니다. 리팩토링은 현재 동작을 고정하는 특성 테스트, 버그 수정은 버그 때문에 실패하는 재현 테스트, 기능 개발은 승인된 스펙의 요구사항 테스트를 작성하며, 기준 커밋 이후에는 테스트 파일을 고치지 않습니다.
- **이유**: 기준 커밋과 구현 커밋을 분리하면 리뷰 단계에서 "기준 테스트가 바뀌지 않았고 통과한다"만 확인해도 동작 보존과 수정 여부를 바로 판단할 수 있습니다.
- **결과**: #5에서는 재현 테스트 4개가 실패하는 상태를 먼저 커밋했고, #7에서는 특성 테스트 5개를 먼저 커밋한 뒤 테스트 파일을 수정하지 않았습니다.

## 3. 구축 후 일괄 검증(2026-11-20)

- **상황**: 초기 계획은 그룹 A를 도입해 검증한 뒤 B, C로 넘어가는 순차 진행이었습니다.
- **결정**: 모든 그룹의 도구를 먼저 완성한 뒤 그룹별 실전 작업을 한꺼번에 검증하는 쪽으로 바꿨습니다. 공통 뼈대 확인용으로 그룹 A만 1건(#5) 먼저 돌려봤습니다.
- **이유**: 상태 파일, 리뷰 흐름, 문서 교정 같은 공통 절차가 B, C를 구현하는 과정에서 계속 바뀌었기 때문입니다. 단계마다 검증을 반복하면 공통 절차가 바뀔 때마다 앞선 검증을 다시 수행해야 합니다.
- **결과**: 일괄 검증에서 발견되는 결함은 모아서 한 번에 보완합니다.

## 4. 수동 승인 범위(2026-11-18)

- **상황**: 작업 루프 전체를 완전 자동화할 수도 있지만, 변경이 의도에 부합하는지 최종 판단하는 역할은 아직 수동으로 두어야 합니다.
- **결정**: 도입 초기에는 정기 스캔과 PR 1차 리뷰만 자동으로 실행하고, 작업 시작, 스펙 승인, 머지, Terraform plan과 apply, 배포는 개발자가 직접 처리합니다.
- **이유**: 되돌리기 어려운 결정을 수동 승인으로 남겨 두면 AI가 잘못 판단하더라도 영향 범위가 PR 내부로 제한됩니다.
- **결과**: 작업 유형별로 AI PR의 무수정 승인율을 추적합니다. 자동화 확대 기준(최근 10건 무수정 승인, 회귀 0건)은 아래 "남은 결정"에 남겨 두었습니다.

## 5. 역할별 모델 배치(2026-11-18)

- **상황**: 모든 단계에 최상위 모델을 쓰면 사용 한도가 빠르게 소진되고, 단일 세션이 길어질수록 누적된 파일 내용 때문에 컨텍스트 품질이 떨어집니다.
- **결정**: 코드 탐색은 Haiku, 기준이 고정된 뒤의 구현과 테스트 작성은 Sonnet, 오케스트레이션과 리뷰는 Opus에 맡겼습니다. 서브에이전트는 읽은 파일을 그대로 넘기지 않고 근거(`경로:줄`)가 붙은 요약만 반환합니다.
- **이유**: 파일을 많이 훑고 짧게 요약하는 탐색 작업은 경량 모델로 충분하며, 리뷰어는 작성자보다 추론 능력이 떨어지면 안 되므로 Opus로 고정했습니다.
- **결과**: `.claude/agents/` 정의 파일에 모델과 추론 강도(`effort`)를 명시했습니다. 리뷰어는 코드를 수정할 수 없고, 파일 읽기와 읽기 전용 git 명령(`diff`, `log`, `show` 등)만 전용 hook 제어 아래 사용합니다.

- **이유**: 서브에이전트 보고만 신뢰하면 실제로 실행되지 않은 검증 결과가 PR 본문에 통과로 기록될 위험이 큽니다.
- **결과**: `playbooks/group-a.md`와 에이전트 지침에 반영했습니다. #7에서도 구현 에이전트가 종료 코드를 누락했지만, 오케스트레이터가 직접 실행해 수치를 확인했습니다.

## 7. 기존 계층 위반 동결(2026-11-18)

- **상황**: 계층 규칙 테스트(ArchUnit)를 처음 도입했을 때, `application`이 `presentation`이나 `infrastructure`에 의존하는 기존 위반이 34개 클래스, 176건 있었습니다.
- **결정**: 기존 위반은 현재 상태로 동결하고 신규 위반만 테스트 실패로 처리합니다. 동결 목록(`archunit_store`)에 위반을 수동 추가하는 행위는 금지합니다.
- **이유**: 기존 위반을 한꺼번에 손대면 PR 규모가 커지고 동작이 깨질 위험이 높습니다. 동결로 현 상태 악화를 막아 두고, 하네스 검증 이후 리팩토링 트랙에서 점진적으로 해소하는 편이 안전합니다.
- **결과**: 동결 위반 수를 주간 지표로 추적합니다. 기존 위반을 해결하면 동결 목록에서 자동으로 제거됩니다.

## 8. 이벤트 스키마 스냅샷 테스트(2026-11-19)

- **상황**: Kafka 이벤트 클래스는 여러 서비스가 공유하므로 필드 하나만 바뀌어도 다른 서비스 소비자가 깨질 수 있습니다.
- **결정**: 이벤트 직렬화 구조를 스냅샷 파일로 고정해 구조 변경 시 테스트가 실패하도록 만들고, API 스키마는 컨트롤러 테스트로 고정합니다.
- **이유**: 별도 스키마 레지스트리 인프라를 올리지 않고도 기능 개발 과정에서 의도치 않은 이벤트 계약 파손을 기계적으로 검출할 수 있습니다.
- **결과**: `EventSchemaSnapshotTest`가 이벤트 스키마를 검증합니다. 의도된 변경일 때만 스냅샷을 갱신해 함께 커밋합니다.

## 9. 인프라 작업의 클라우드 자격 증명 미부여(2026-11-19)

- **상황**: 인프라 변경을 검증하려면 Terraform plan이 필요하지만, plan 실행에는 클라우드 자격 증명이 요구됩니다.
- **결정**: AI에는 클라우드 자격 증명을 부여하지 않습니다. AI는 자격 증명 없이 도는 로컬 검증(`terraform fmt`, `validate`, `test`)과 예상 plan 요약까지만 작성하고, 실제 plan은 개발자가 CI에서 실행한 뒤 결과를 넘겨 대조하게 합니다. 격리 실행 환경은 로컬 compose만 사용합니다.
- **이유**: 자격 증명이 세션에 노출되어 있으면 hook 차단이 우회될 때 실제 클라우드 리소스가 변경될 수 있습니다. 권한 자체를 주지 않는 편이 확실합니다.
- **결과**: hook이 `terraform plan/apply/destroy`와 클라우드 CLI 쓰기 명령을 차단합니다.

## 11. 이종 모델(Gemini) 기반 문서 교정(2026-11-19, 2026-11-20 갱신)

- **상황**: AI가 작성한 PR 본문과 문서는 서술어 누락이나 맥락 없는 짧은 문장이 자주 섞여 나오고, 작성한 모델 스스로는 이 문제를 잘 잡아내지 못합니다.
- **결정**: PR 직전에 사람이 읽는 문서를 이종 모델(Gemini, Antigravity CLI)로 교정합니다. 변경분만 묶어 일괄 호출하며, 교정 기록이 없으면 PR 생성을 차단합니다. 기본 모델은 `gemini-4-neon-medium`입니다.
- **이유**: 경량 Gemini 모델(hydrogen)과 고성능 모델(neon)을 비교한 결과(이름 끝의 `medium`, `high`는 추론 강도(reasoning effort)), hydrogen은 명백한 오탈자만 잡고 서술어 누락이나 의미 중복 같은 문맥 결함을 놓쳤습니다. Antigravity CLI는 호출당 고정 비용(입력 약 1.1만 토큰, 약 10초)이 커서 호출 횟수를 줄이는 배치 구조로 설계했습니다.
- **결과**: 호출 수를 18회에서 3회로 줄이면서도 심은 오류 10개를 모두 검출했습니다. 상세 측정치는 [metrics.md](metrics.md)에 있습니다.

## 12. 이종 모델(Gemini) 기반 코드 2차 리뷰(2026-11-20)

- **상황**: Claude 리뷰어만 사용하면 같은 모델 계열 특성상 놓치는 맹점이 겹칠 수 있습니다. 그렇다고 CI에서 Gemini를 돌리려면 별도 API 키나 GCP 자격 증명이 필요하며, 개인 구독 계정을 CI에 연동할 공식 경로가 없습니다.
- **결정**: Claude 리뷰어 통과 후 PR 직전에 로컬 환경에서 Gemini(`gemini-4-neon-high`)로 2차 리뷰를 수행합니다. 열린 PR에서는 오탐을 걸러낸 결과만 PR 리뷰 코멘트로 게시합니다. 기존 Claude CI 리뷰는 유지하고, 장기적으로 어느 쪽을 주력으로 둘지는 추후 판단합니다.
- **이유**: 공개 저장소에 self-hosted runner를 연결하면 외부 PR이 로컬 머신에서 임의 코드를 실행할 보안 위험이 있어 채택하지 않았습니다.
- **결과**: 버그 4개를 심은 브랜치에서 4개를 모두 검출했고, [PR #12](https://github.com/bstaran/CC-Creator-Culture/pull/12)에서는 Claude 리뷰어가 놓친 실제 버그 2건을 찾아냈습니다.

## 13. 변경된 파일 중심의 정기 스캔(2026-11-20)

- **상황**: 매주 코드베이스 전체를 스캔하면 토큰 소모가 과하고, 진단 후보를 전부 이슈로 자동 등록하면 불필요한 백로그가 쌓입니다.
- **결정**: 주간 스캔은 지난 7일간 변경된 소스 파일만 진단합니다. 후보는 주간 리포트 이슈의 체크 목록으로 올리고, 체크박스로 승인된 항목만 이슈로 생성합니다. 수치 지표 수집은 AI 없이 스크립트로 처리합니다.
- **이유**: 최근 수정된 파일에 새 결함이 유입될 가능성이 가장 높고, 체크박스 승인으로 선별 단계를 지키면서도 운영 부담을 줄일 수 있기 때문입니다.
- **결과**: `.github/workflows/ai-weekly.yml`로 구현했습니다. CI 토큰 복구 후 첫 실전 실행을 검증할 예정입니다.

## 14. 파괴적 명령의 이중 차단(2026-11-20)

- **상황**: hook으로 명령을 검사하더라도 셸 표현이나 옵션을 변형하면 우회할 수 있습니다. CI 연동 리뷰([PR #14](https://github.com/bstaran/CC-Creator-Culture/pull/14))에서도 push 차단을 우회하는 패턴이 지적됐습니다.
- **결정**: hook에서는 확인된 우회 형태(force push 변형, 원격 브랜치 삭제, git config를 통한 명령 실행 등)를 계속 막고 차단/허용 케이스를 회귀 테스트로 고정합니다. 동시에 GitHub의 `dev`, `main` 브랜치 보호를 최종 경계로 둡니다. CI에서도 기본 워크플로우 토큰은 읽기 전용으로 제한하고, push와 PR 생성은 Claude GitHub App 토큰으로만 수행합니다.
- **이유**: 문자열 파싱만으로는 모든 우회 가능성을 원천 차단할 수 없으므로, AI 측 hook과 저장소 권한 경계를 이중으로 두어야 한쪽이 뚫려도 사고를 막을 수 있습니다.
- **결과**: 차단 규칙 회귀 테스트를 65개에서 100개로 확충했습니다.

## 16. 사람용 글 작성의 이종 모델 위임(2026-11-23)

- **상황**: 11번 결정 이후에도 Claude가 쓴 글은 교정을 거쳐도 문장 구조와 말투(메타 도입문, 기계적인 나열)가 남았습니다. 교정은 한 줄 단위 제안이라 글 전체의 흐름을 바꾸기 어려웠습니다.
- **결정**: PR 본문, 이슈 본문, `docs/` 문서, README, 작업 기록은 Gemini가 작성합니다. Claude는 사실 초안을 만들고 결과물의 사실만 대조하며, 문장은 고치지 않습니다. AI가 읽는 지침(`CLAUDE.md`, `.claude/`, `playbooks/`)은 Claude가 계속 작성합니다.
- **이유**: 테스트 수, 경로, 실행 결과는 Claude가 직접 실행해 얻은 값이라 Gemini가 다시 알아낼 수 없습니다. 글을 쓰는 모델이 숫자나 경로를 바꿀 위험이 있으므로 역할을 나누고 사실을 기계적으로 검사합니다.
- **결과**: `scripts/ai/doc-write.py`가 결과물에 사실 초안과 참고 문서에 없던 숫자, 백틱 안 내용, 링크, `#번호`가 생기면 이유를 붙여 한 번 다시 쓰게 하고, 그래도 어긋나면 결과물을 사용하지 않습니다. 사실 검사를 통과한 글은 작성 기록으로 남아 PR 생성 hook을 통과합니다. CI에는 `agy`가 없어 Claude가 직접 작성하고 "건너뜀"으로 기록합니다.
