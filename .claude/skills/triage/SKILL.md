# /triage

요청: `$ARGUMENTS`

작업을 시작하기 전에 **완료 판단 기준**을 정하는 단계다. 이 단계에서는 코드를 수정하지 않는다.
분류 기준의 원본은 `docs/ai-system/plan.md` 3장과 7장이다.

## 0. 저장소 확인

GitHub CLI(`gh`) 명령에는 항상 `--repo`를 붙인다. 대상은 팀 원본 저장소가 아니라 **`origin` 원격 저장소**다.

```bash
git remote get-url origin   # 예: https://github.com/<owner>/<repo>.git → --repo <owner>/<repo>
```

## 1. 요청 파악

- **이슈 번호 입력**: 본문과 코멘트를 모두 읽는다.
  ```bash
  gh issue view <번호> --repo <repo> --comments
  ```
- **복합 요청 분리**: 요청에 여러 작업이 섞여 있으면 항목별로 나눈다. 항목 하나당 트랙 하나를 배정한다.

## 2. 중복 확인

```bash
gh issue list --repo <repo> --state open --search "<핵심 키워드>" --limit 20
```

같은 일을 다루는 열린 이슈가 있으면 새로 만들지 않고, 기존 이슈를 이어서 진행하거나 기존 이슈에 코멘트로 통합하자고 제안한다.

## 3. 범위 확인

- **범위가 분명할 때**: 직접 `Grep`/`Read`로 확인한다.
- **여러 서비스에 걸치거나 불명확할 때**: `explorer` 에이전트에 서비스별로 나눠 탐색을 맡긴다(요약만 받는다).
- **필수 점검 대상**:
  - 대상 모듈, 관련 클래스, 기존 테스트 유무
  - Kafka 이벤트, Feign, 게이트웨이 라우트, Flyway, 보안 설정의 연관 여부

## 4. 트랙 분류

| 판단 질문 | 트랙 | 그룹 |
|---|---|---|
| 동작은 그대로 두고 구조만 바꾸는가 | 리팩토링 | A |
| 기대 동작이 코드, 문서, 테스트, 스펙 어딘가에 이미 정해져 있는데 현재 동작이 다른가 | 버그 수정 | A |
| 새 동작(API, 이벤트, 화면 흐름, 정책)을 만들거나 기대 동작 자체가 아직 정해지지 않았는가 | 기능 개발 | B |
| 코드 변경 없이 답이나 문서가 결과물인가 | 조사/문서 | B |
| Terraform, 워크플로우, Dockerfile, compose, 배포 스크립트, `config-repo/*-prod.yaml`을 바꾸는가 | 인프라/배포 | C |
| 응답 시간, 처리량, 자원 사용량이 문제인가 | 성능 | C |

### 경계 모호 시 분류 규칙
- **근거 없는 "버그" 제보**: 기대 동작을 정한 근거가 없으면 **기능 개발(B)**로 분류해 스펙부터 정한다.
- **성능 문제**: 원인이 코드에 있어 보여도 먼저 **성능(C)** 트랙으로 기준선을 측정한다.
- **리팩토링 중 버그 발견**: 둘을 분리한다. 리팩토링은 기존 버그까지 그대로 보존하고, 발견한 버그는 별도 항목으로 올린다.

## 5. 기준, 규모, 리뷰어 결정

| 트랙 | 먼저 고정할 기준 |
|---|---|
| 리팩토링 | 대상 동작을 덮는 특성 테스트(현재 코드에서 통과) |
| 버그 수정 | 실패하는 재현 테스트(현재 코드에서 버그 때문에 실패) |
| 기능 개발 | 승인된 스펙(완료 조건), 요구사항 테스트, API/이벤트 스키마 |
| 조사/문서 | 답할 질문의 범위 |
| 인프라/배포 | 변경 의도와 예상 plan 차이 |
| 성능 | k6 시나리오와 기준선, 목표 수치 |

- **규모**:
  - **작음**: 단일 모듈, 파일 몇 개 수준, 기준 명확 → 현재 세션에서 바로 처리
  - **큼**: 그 외 → 상태 파일과 worktree를 쓰는 파이프라인으로 처리
- **리뷰어**: 코드 변경은 `arch-reviewer`가 항상 검토한다. Kafka/outbox, `/internal` API, 스키마, 인프라가 연관되면 위험 요소로 적는다 *(전용 리뷰어는 이후 단계에서 추가된다)*.
- **난이도(모델)**: 서비스 간 설계 변경, 동시성(주문, 쿠폰 Lua, outbox) 문제는 `"난제"`로 표시한다.

## 7. 다음 단계 진행

보고한 뒤 사용자가 다음 진행 방식을 선택하도록 한다. **사용자 승인 없이 이슈, 라벨, 브랜치, 코드 변경을 만들지 않는다.**

### ① 이슈로 등록
- 제목: `<type>(<scope>): <요약>`
- 라벨: 트랙 라벨 + `source: ad-hoc`
  - 트랙 라벨: `type: refactor`, `type: bug`, `type: feature`, `type: research`, `type: infra`, `type: perf`
- 본문: `.github/ISSUE_TEMPLATE/ai-request.md` 구조에 분류 결과를 붙인다.

```bash
gh issue create --repo <repo> --title "fix(order): ..." --label "type: bug" --label "source: ad-hoc" --body-file <임시 파일>
```

### ② 지금 진행
- **조사/문서**: 바로 답한다. 모든 주장에 `경로:줄` 근거를 붙인다. 결과를 문서 파일로 남기면 확정 전에 `/doc-review`로 문장을 다듬는다.
- **리팩토링, 버그 수정**: `docs/ai-system/tasks/_template.md`를 복사해 상태 파일을 만든 뒤, `test-writer`(기준 테스트) → `implementer`(구현) → `arch-reviewer`(리뷰, 수정 요청 최대 2회) 순서로 진행한다.
- **기능 개발**: 구현하지 않는다. 스펙 초안(완료 조건, API/이벤트 스키마)을 작성해 승인을 요청하는 단계까지만 진행한다.
- **인프라/배포**: 변경 초안과 로컬 검증(`fmt`, `validate`, `test`)까지만 한다. `plan`, `apply`, 배포는 사람이 CI에서 한다.
- **성능**: 측정 계획(시나리오, 반복 횟수, 비교 기준)을 먼저 확인받는다.

### ③ 보류
- 분류 결과만 남기고 종료한다.
