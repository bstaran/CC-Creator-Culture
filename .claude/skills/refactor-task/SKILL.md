# /refactor-task

이슈: $ARGUMENTS

`docs/ai-system/playbooks/group-a.md`를 읽고 그 절차를 따른다. 아래는 리팩토링에만 해당하는 내용이다.

## 시작 전 확인

- 이슈 라벨이 `type: refactor`인지 확인한다. 아니면 멈추고 `/triage`를 제안한다.
- 리팩토링의 정의: **외부에서 관찰되는 동작이 바뀌지 않는다.** 공개 API(경로, 요청/응답 필드, 상태 코드), 예외 타입과 에러 코드, 이벤트 페이로드와 토픽, DB 스키마와 쿼리 결과, 로그로 의존하는 동작이 모두 그대로여야 한다.
- 이 중 하나라도 바뀌어야 한다면 리팩토링이 아니다. 멈추고 기능 개발이나 버그 수정으로 다시 분류하자고 보고한다.
- 작업 중 버그를 발견하면 고치지 않는다. 특성 테스트에 현재 동작 그대로 고정하고, 별도 `type: bug` 이슈 후보로 상태 파일과 PR 참고사항에 적는다.

## 3단계(기준 고정)

1. 변경할 클래스와 그 호출자를 정한다(`explorer` 활용).
2. 기존 테스트와 커버리지로 충분한지 판단한다. 판단 기준: 바꿀 메서드의 공개 동작(정상, 예외, 경계값, 이벤트 발행)이 테스트로 검증되는가.
3. 부족하면 `/characterize` 절차로 특성 테스트를 추가하고 `test(<scope>): #<번호> 특성 테스트`로 커밋한다. 충분하면 어떤 테스트가 기준인지 상태 파일에 적는다.

## 4~6단계에서 특히 볼 것

- `implementer`에게 "동작 변경 금지, 기준 테스트 수정 금지, 범위 밖 정리 금지"를 명시한다.
- 검증 후 테스트 수가 줄지 않았는지, 기준 테스트 파일이 3단계 커밋 이후 바뀌지 않았는지 확인한다.
  ```bash
  git diff <특성 테스트 커밋>..HEAD --stat -- '*/src/test/**'
  ```
- ArchUnit 동결 저장소가 줄었다면(위반 해소) 그 변경을 함께 커밋하고 PR에 몇 건이 줄었는지 적는다.
- 리뷰어: `arch-reviewer`(5번 항목 "리팩토링: 동작이 바뀌지 않았는가"를 중점으로 요청). 이벤트, outbox, Lua, `/internal`이 걸리면 `event-reviewer`도.

## PR

- 제목: `refactor(<scope>): <요약>`
- 본문 참고사항에 "동작 변경 없음"의 근거(기준 테스트 목록, 전후 테스트 수)를 적는다.
