# /bugfix

이슈: $ARGUMENTS

`docs/ai-system/playbooks/group-a.md`를 읽고 그 절차를 따른다. 아래는 버그 수정에만 해당하는 내용이다.

## 시작 전 확인

- 이슈 라벨이 `type: bug`인지 확인한다. 아니면 멈추고 `/triage`를 제안한다.
- **기대 동작의 근거**를 찾는다: 스펙, 이슈, API 문서, 기존 테스트, 다른 환경의 설정, 코드 주석. 근거가 없으면 버그가 아니라 기대 동작을 새로 정하는 일이다. 멈추고 기능 개발(스펙 승인)로 다시 분류하자고 보고한다.
- 근거와 기대 동작을 상태 파일 "기준"에 적는다.

## 3단계(기준 고정): 재현 테스트

1. 원인 후보를 좁힌다(`explorer` 활용, 근거는 `경로:줄`).
2. `test-writer`에게 **재현 테스트**를 맡긴다. 넘길 것: worktree 경로, 기대 동작과 근거, 현재 동작, 원인 후보.
3. 오케스트레이터가 직접 실행해 확인한다.
   - 현재 코드에서 **실패**해야 한다.
   - 실패 이유가 버그와 같아야 한다(단언 실패 메시지가 기대 동작과 현재 동작의 차이를 보여 줘야 한다). 컴파일 오류, 설정 오류, 타임아웃으로 실패하면 기준이 아니다. 다시 맡긴다.
   - 실패 메시지를 상태 파일에 그대로 기록한다.
4. `test(<scope>): #<번호> 재현 테스트`로 커밋한다. 이 커밋에서는 테스트가 실패하는 것이 정상이다(PR 본문에 명시).

설정 파일(`config-repo/*.yaml`) 버그도 같은 원칙이다. 설정을 읽어 기대 동작을 단언하는 테스트로 재현한다(예: 게이트웨이 라우트 파일 3개를 읽어 특정 경로가 같은 서비스로 라우팅되는지 확인).

## 4~6단계에서 특히 볼 것

- `implementer`에게 "원인만 고치는 최소 변경, 재현 테스트 수정 금지"를 명시한다.
- 검증: 재현 테스트가 통과하고, 같은 모듈의 기존 테스트가 모두 통과해야 한다. 같은 원인이 다른 곳에도 있는지(같은 패턴의 코드, 다른 환경 설정 파일) 확인하고 결과를 상태 파일에 적는다.
- 리뷰어: `arch-reviewer`(5번 항목 "버그 수정: 재현 테스트가 원인을 겨누는가"를 중점으로 요청). 이벤트, outbox, Lua, `/internal`이 걸리면 `event-reviewer`도.

## PR

- 제목: `fix(<scope>): <요약>`
- 본문 "테스트 결과"에 수정 전 재현 테스트 실패 메시지와 수정 후 통과 결과를 함께 적는다.
- 같은 원인의 다른 위치를 고치지 않았다면 그 이유를 참고사항에 적는다.
