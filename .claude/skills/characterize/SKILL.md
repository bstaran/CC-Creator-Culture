# /characterize

대상: $ARGUMENTS

현재 동작을 테스트로 고정해 이후 변경의 기준으로 삼는다. 단독으로 쓰거나 `/refactor-task`의 3단계로 쓴다.

## 1. 대상과 작업 위치

- 이슈 번호면 `gh issue view <번호> --repo <origin 저장소>`로 대상을 확인한다.
- worktree 경로가 주어지면 그 안에서 작업한다. 없으면 현재 체크아웃에서 작업하되, 현재 브랜치가 `dev`나 `main`이면 멈추고 작업 브랜치를 만들자고 제안한다.

## 2. 현재 테스트 상태 파악

- 대상 클래스를 직접 쓰는 테스트를 찾는다(`explorer`에 맡겨도 된다).
- 커버리지를 확인한다.
  ```bash
  ./gradlew :<모듈>:test
  python3 scripts/ai/coverage-summary.py --top 40   # 대상 패키지 줄을 확인
  ```
  클래스 단위가 필요하면 `<모듈>/build/reports/jacoco/test/html/<패키지>/<클래스>.html`을 본다.
- 덮이지 않은 공개 메서드, 분기, 예외 경로, 이벤트 발행, 외부 호출 결과 처리를 목록으로 만든다.

## 3. 특성 테스트 작성(`test-writer`)

`test-writer`에 넘길 것:
- 작업 디렉터리 경로, 대상 클래스와 메서드, 2단계의 덮이지 않은 목록
- 종류: **특성 테스트**(현재 코드에서 통과해야 함)
- "이상해 보이는 동작도 지금 동작 그대로 고정하고, 의심스러운 점은 발견한 점에 적는다"

## 4. 확인

- 새 테스트가 현재 코드에서 모두 통과하는지 직접 실행해 확인한다. 건너뛴 테스트가 없는지 `build/test-results`에서 본다.
- 커버리지를 다시 측정해 전후 수치를 기록한다.
- 기준이 실제로 동작을 잡는지 한 번 점검한다: 대상 코드의 핵심 분기 하나를 임시로 바꿔 새 테스트가 실패하는지 보고, 즉시 되돌린다(되돌린 뒤 `git diff`로 `src/main` 변경이 없는지 확인).

## 5. 보고

```
## 특성 테스트
| 항목 | 값 |
|---|---|
| 대상 | `클래스#메서드` ... |
| 추가 테스트 | `경로` (N개) |
| 결과 | 통과 N / 건너뜀 0 |
| 커버리지 | 라인 a% → b%, 분기 c% → d% (대상 클래스 기준) |
| 변이 점검 | 어떤 분기를 바꿨고 몇 개 테스트가 실패했는지 |

## 발견한 의심 동작
- (버그로 보이는 동작. 고치지 않고 별도 `type: bug` 이슈 후보로 남긴다)
```

상태 파일이 있으면 같은 내용을 진행 로그에 남긴다. 커밋은 호출한 스킬(또는 사용자)이 정한다.
