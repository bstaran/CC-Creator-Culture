# /spec

요청: $ARGUMENTS

`docs/ai-system/playbooks/group-b.md` 1장을 따른다. 이 스킬은 **코드를 고치지 않는다.**

## 1. 요청 파악

- 이슈 번호면 본문과 코멘트를 읽는다: `gh issue view <번호> --repo <origin 저장소> --comments`
- 기능 개발이 맞는지 확인한다. 기대 동작의 근거가 이미 있는데 지금 다르게 동작한다면 버그(`/bugfix`)다.
- 모호한 점은 추측해서 채우지 않는다. 질문 목록으로 모아 스펙의 "확인 필요" 항목에 남긴다.

## 2. 현황 조사

`explorer`에게 영향 범위 조사를 맡긴다(서비스가 여러 개면 서비스별로 병렬 진행한다).
- 관련 도메인의 현재 API, 엔티티, 이벤트, 권한 규칙
- 비슷한 기존 기능의 구현 방식(따라야 할 관례)
- 변경 시 영향을 받는 생산자/소비자, 호출자/제공자

## 3. 스펙 초안

`.github/ISSUE_TEMPLATE/spec.md`의 구조를 그대로 쓴다.
- **완료 조건**: AC1, AC2 등으로 번호를 붙인다. 각 AC는 확인 가능한 결과 하나로 작성한다. 정상, 예외(권한 없음, 검증 실패, 없는 리소스), 경계값을 빠뜨리지 않는다.
- **API 변경**: 메서드, 경로, 권한(역할), 요청 필드(필수 여부), 응답 필드, 오류(상태 코드, 에러 코드)를 적는다. 응답은 `ApiResponse`, 목록은 `PageResponse` 관례를 따른다.
- **이벤트 변경**: 하위 호환(필드 추가만)을 기본으로 한다. 하위 호환을 깨는 변경이 필요하면 이유와 이행 방법을 적는다.
- **DB 변경**: 새 Flyway 버전, 기존 데이터 처리, 배포 중 구버전과의 공존 가능 여부를 적는다.
- **범위 밖**과 **확인 필요(질문)**를 따로 적는다.

위 내용은 사실 초안(`.ai-cache/brief/spec-<이름>.md`)으로 정리하고, 이슈 본문은 `/doc-write`로 쓴다(양식: `.github/ISSUE_TEMPLATE/spec.md`).

## 4. 등록과 승인 요청

- 사용자에게 초안을 보여 주고, 등록 방식을 확인한다. **승인 없이 이슈를 만들거나 고치지 않는다.**
  - 새 이슈: `gh issue create --repo <origin 저장소> --title "feat(<scope>): ..." --label "type: feature" --label "source: ad-hoc" --body-file <파일>`
  - 기존 이슈: 스펙을 코멘트로 남기거나, 사용자가 원하면 본문을 갱신한다.
- 담당자가 `spec: approved` 라벨을 붙이면 `/feature #<번호>`로 진행한다고 안내한다. **AI는 이 라벨을 붙이지 않는다.**
