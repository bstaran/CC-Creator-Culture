# /gemini-review

대상: $ARGUMENTS

Claude와 다른 모델의 **두 번째 의견**을 받는다. 모델은 읽기만 하고(plan 모드, 셸 명령은 자동 거부), 코멘트 게시는 스크립트가 한다.

## 1. 실행

```bash
python3 scripts/ai/code-review.py --out <스크래치>/review.json            # 현재 브랜치(커밋된 변경, origin/dev 기준)
python3 scripts/ai/code-review.py --pr <번호> --out <스크래치>/review.json # PR(임시 worktree에 head를 받아 리뷰)
```

- 대상은 코드, 설정, SQL, 스크립트다. 문서(`*.md`), 동결 저장소, 이벤트 스냅샷, 바이너리는 빠진다. 문서는 `/doc-review`가 맡는다.
- 기본 모델은 `gemini-4-neon-high`다. 묶음(diff 600줄) 하나에 2~7분이 걸리므로 **백그라운드로 실행**하고 완료 알림을 기다린다. 빠른 확인만 필요하면 `--model gemini-4-neon-medium`(1분 안팎, 미묘한 지적은 놓친다)을 쓴다.
- 종료 코드 3(`skipped`, `error`)이면 리뷰를 건너뛰고 그 사실만 보고한다. 이 단계 때문에 작업을 멈추지 않는다.
- 스크립트가 위치가 틀린 지적은 버리고, diff 밖 위치는 본문 지적(`inline: false`)으로 돌린다. 버린 개수는 `filtered`에 있다.

## 2. 판단(Claude)

지적마다 해당 코드를 직접 열어 확인하고 셋 중 하나로 판정한다. 모델의 근거(`evidence`)를 그대로 믿지 않는다.

| 판정 | 기준 |
|---|---|
| 타당 | 코드에서 문제를 확인했다(입력이나 상황을 구체적으로 말할 수 있다) |
| 오탐 | 코드나 설정이 이미 처리하고 있다, 전제가 틀렸다, 레포 규칙과 맞지 않는 제안이다 |
| 보류 | 맞는 말이지만 이번 변경의 범위 밖이거나, 설계 결정이 필요하다 |

## 3-1. 현재 브랜치(파이프라인의 PR 직전)

- 타당한 `blocker`, `major`는 고친다. 고친 뒤에는 파이프라인의 검증 단계(빌드, 테스트)를 다시 실행한다. Gemini 리뷰는 다시 돌리지 않는다.
- `minor`는 고칠지 판단하고, 고치지 않은 지적은 PR 본문 참고사항에 적는다.
- 리팩토링 트랙에서 동작을 바꿔야 하는 지적은 고치지 않고 `type: bug` 후보로 보고한다.
- PR 본문 참고사항에 한 줄로 남긴다: `Gemini 리뷰(<모델>): 지적 n건, 반영 n, 오탐 n, 보류 n`과 보류 이유.

## 3-2. PR(`#번호`)

- 판정 표를 보여 준 뒤, 오탐을 뺀 나머지를 게시한다. `--no-post`가 있으면 게시하지 않고 보고만 한다.
  ```bash
  python3 scripts/ai/code-review.py --post-from <스크래치>/review.json --pr <번호> --drop <오탐 id,...>
  ```
- 리뷰한 뒤 PR에 새 커밋이 올라왔으면 스크립트가 게시를 거부한다. 다시 리뷰한다.
- 게시는 `COMMENT` 리뷰 하나로 올라간다(승인이나 변경 요청이 아니다). diff 줄에 달 수 있는 지적은 줄 코멘트로, 나머지는 리뷰 본문에 들어간다.
- 코드 수정은 하지 않는다. 고칠 필요가 있으면 PR 작성자(또는 해당 트랙 파이프라인)에게 넘긴다.

## 4. 보고

```
## Gemini 리뷰(<모델>)
파일 <n>개, 호출 <n>회, <초>초, 입력 <토큰>, 생각 <토큰>
| id | 위치 | 심각도 | 지적 | 판정 | 이유 |
|---|---|---|---|---|---|

조치: 반영 <n>, 오탐 <n>(게시 제외), 보류 <n>. 게시: <리뷰 링크 또는 "안 함">
```

작업 상태 파일이 있으면 진행 로그에 한 줄로 남긴다(모델, 지적 수, 판정 결과).
